<recorded_decisions>
Discretionary constants, locked so the executor implements one concrete thing.
All are read from prefs (04-03 ships the defaults) rather than written as literals
in code, so Phase 5 can tune them without touching the supervisor:

- Startup gate poll interval **250 ms**, startup gate cap **90 s** (sized from the
  measured cold-start figure recorded in `04-02-SUMMARY.md`).
- Steady-state poll interval **5000 ms**; a single health request times out after
  **4000 ms**, so a probe can never overlap the next one.
- Restart backoff: **500 ms** initial, doubling, capped at **5000 ms**, retrying
  **indefinitely** — Phase 4 has no give-up threshold (D-103).
- Kill grace **3000 ms**, passed as the single argument to the platform kill call.
- Ring buffer **500 lines**, oldest dropped first.
- Token minted once per browser launch with the chrome global `crypto.randomUUID()`
  — a plain global, not one of D-96's forbidden internals.
- A restart is triggered by **two consecutive** failed steady-state probes, not
  one, so a single slow response does not churn a healthy backend.
</recorded_decisions>

  <action>
Extend `TheiaService` with the steady-state loop and the restart path.

After the swap, switch the health probe from the startup interval to the
steady-state interval, both read from prefs. Each probe carries the token as a
request header and has its own bounded timeout, so a probe can never overlap the
next one.

Treat two consecutive failed probes as a dead backend. On that transition, reap the
current process handle if it still exists, then respawn with the same port and the
same token, and resume probing at the startup interval until a probe passes, then
return to the steady-state interval. Between failed respawn attempts wait the
current backoff, doubling from the initial value up to the cap, resetting to the
initial value on the first successful probe. Retry indefinitely — Phase 4 has no
give-up threshold, and no branded error state; both are Phase 5's SHELL-03.

The port is pinned for the whole browser session. The first spawn is the only one
that passes port zero; every subsequent spawn passes the port learned from that
first spawn's sentinel, because the already-loaded Theia page reconnects to the
origin it was loaded from and a fresh port would make that reconnect impossible.
The token is pinned the same way, so the cookie set before first navigation keeps
working across every restart.

Do nothing visually on a mid-session restart: the loading layer must not reappear
and the browser element must not be re-navigated. Theia's own reconnect UI owns
that gap (D-95).

If a respawn's sentinel reports a port different from the pinned one, treat it as a
hard error: log it loudly into the ring buffer and keep retrying on the pinned port
rather than silently following the new one — a moved port means the loaded page can
never reconnect. The case where the pinned port has been taken by another process
is explicitly out of scope for Phase 4 and belongs to Phase 5's exhausted-backoff
handling; record it in the summary as a known residual risk rather than handling it
here.
  </action>

  <action>
Close the lifecycle.

Register the quit observer through `SourcererAPI.onQuitGranted` during `start()`.
Its callback runs `stop()`, which must do three things in this order: cancel the
health-loop timer and set a shutting-down flag so no restart can begin; signal the
backend by calling `SourcererAPI.killProcess` with the grace period read from
prefs; then await the process's exit. That single kill call already sends the
terminate signal, waits the grace, and force-kills — do not wrap it in a timer of
your own. The whole sequence is bounded by the grace period, so quit can never hang
the browser. Observe the topic that fires once quit is final and can no longer be
cancelled, not the earlier cancellable one: beginning an irreversible shutdown
under a quit that gets aborted would kill a backend the user still wants.

Finish the ring buffer. It already exists from Task 1's pipe reader; make its size
come from `sourcerer.sidecar.logBufferLines`, drop oldest first, and expose
`getRecentLog()` returning the buffered lines newest-last. Also expose `getState()`
returning the current port, pid, health status and restart count. Phase 5's
diagnostics page reads both — build them now so there is nothing to retrofit, but
build no page and no UI for them in this phase.

Keep all of it in memory. Nothing here writes a file, and nothing depends on
Firefox's session store: the storage ground stays unbuilt-on for the future unified
store (D-107).
