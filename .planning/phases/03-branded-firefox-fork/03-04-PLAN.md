## Shared-state rule for this plan

This plan runs in the same wave as plan `03-02`, which is driving live browser
sessions against `objdir/` and reading `upstream/`. **Nothing in this plan may
mutate `upstream/` or `objdir/`.** Every control and every test in this plan
runs against a `mktemp -d` git fixture, and `scripts/rebase-upstream.sh` is
exercised only in `--dry-run` mode locally. Its first real run is the CI run.

  <name>Task 1: scripts/rebase-upstream.sh — the one documented rebase command</name>
  <files>scripts/rebase-upstream.sh</files>
  <read_first>

  </read_first>
  <action>
Write `scripts/rebase-upstream.sh` (`set -euo pipefail`, `REPO_ROOT` idiom,
`chmod +x`) taking `--tag <NEW_TAG>` and an optional `--dry-run`.

Real mode, in order:
1. Verify the requested tag exists on the remote with `git ls-remote --tags`,
   failing by name if it does not — cheaper than discovering it after a 1.1 GB
   clone.
2. Remove `upstream/` and re-materialize it at the new tag by invoking
   `TAG="$NEW_TAG" scripts/fetch-upstream.sh`. That override only works because
   plan `03-01` Task 2 changed line 7 to `TAG="${TAG:-…}"`; before that change
   the exported value was clobbered before use and this step would have silently
   re-cloned the **old** tag, replayed onto it cleanly and exited 0 having
   performed no rebase. If `grep -c 'TAG="\${TAG:-' scripts/fetch-upstream.sh`
   is not 1, stop — do not work around it here.
   `upstream/` is fully disposable and gitignored (D-01/D-74); no commit ever
   lives inside it, so there is nothing to preserve. The same script re-creates
   the `upstream/sourcerer` branding overlay symlink on the fresh clone.
3. Replay the stack with `scripts/apply-patches.sh`. Its post-apply per-patch
   assertion is what makes a patch upstream has adopted fail loudly by name
   rather than vanish — do not reimplement that logic here, and do not add a
   fallback that continues past a failed patch.
4. Run `scripts/check-patch-surface.sh` as a final gate, so a rebase can never
   quietly widen the patch surface into compiled files.
5. Re-run `TAG="$NEW_TAG" scripts/fetch-upstream.sh` — passing the **new** tag,
   not the pinned default — and require it to report the fully-applied state,
   which is 03-01 Task 2's classifier confirming the post-rebase tree is exactly
   the stack and nothing more. A `--depth 1 --branch <NEW_TAG>` clone does not
   contain the old tag's ref, so a bare re-run would hard-fail at the identity
   check even on a perfectly correct rebase.
5b. Assert the branding overlay resolves: `readlink -f upstream/sourcerer` must
   print the repo's `sourcerer/` directory. This gate is not optional. The path
   is git-excluded, so a missing symlink is invisible to `git status --porcelain`
   and therefore to step 5's classifier — without this assertion the script would
   exit 0, CI would report success, and the tree would be silently unconfigurable,
   failing later during moz.build traversal rather than cleanly at configure.
6. Print the toolchain re-verification instruction: PITFALLS #2 requires
   `scripts/toolchain-baseline.sh` output to be diffed against
   `toolchain-baseline.txt` after every ESR rebase, and that step needs the Nix
   Gecko toolchain, so state it as the operator's next command rather than
   pretending it ran.

`--dry-run` performs step 1 and then prints the exact commands steps 2-6 would
run, without removing `upstream/` or applying anything. This is the only mode
that may be run locally while another plan is using the tree.

Every failure follows the `rebase-upstream: FAIL -- <cause>` convention with an
indented remediation line. Do not build a stateful rebase branch inside
`upstream/`: D-74 rejects it, and it can be reconstructed from `patches/` at any
later point if the first real rebase proves it necessary.
  </action>
  <verify>
    <automated>bash scripts/rebase-upstream.sh --tag FIREFOX_153_1_0esr_RELEASE --dry-run &amp;&amp; bash scripts/rebase-upstream.sh --tag FIREFOX_153_2_0esr_RELEASE --dry-run | grep -q FIREFOX_153_2_0esr_RELEASE &amp;&amp; ! bash scripts/rebase-upstream.sh --tag NO_SUCH_TAG_XYZ --dry-run</automated>
  </verify>
  <acceptance_criteria>
    - `bash scripts/rebase-upstream.sh --tag FIREFOX_153_1_0esr_RELEASE --dry-run` exits 0 and prints, in order, the fetch, apply, patch-surface, classifier and toolchain-baseline commands it would run.
    - `bash scripts/rebase-upstream.sh --tag NO_SUCH_TAG_XYZ --dry-run` exits non-zero with a `rebase-upstream: FAIL --` message naming the tag.
    - `bash scripts/rebase-upstream.sh --tag <a real ESR tag other than the current pin> --dry-run` prints fetch and re-check commands carrying **that** tag, not `FIREFOX_153_1_0esr_RELEASE`. A dry run that echoes the pinned default is the silent-no-rebase failure this criterion exists to catch.
    - The printed plan includes the `readlink -f upstream/sourcerer` overlay assertion as step 5b.
    - `bash scripts/rebase-upstream.sh` with no `--tag` exits non-zero with a usage message.
    - `git -C upstream status --porcelain` and `git -C upstream rev-parse HEAD` are identical before and after every command run in this task.
    - The script contains no `git rebase`, `git am` or `git cherry-pick` invocation — the replay is `apply-patches.sh` only.
    - The script invokes `scripts/check-patch-surface.sh` and `scripts/apply-patches.sh` rather than reimplementing either.
  </acceptance_criteria>
  <done>One command performs the whole rebase, fails loudly at every step that can fail, and is exercised locally in dry-run without touching the shared tree.</done>

Create `.github/workflows/rebase-upstream.yml`. Trigger: `workflow_dispatch`
**only**. There is no `schedule:` key and must not be one — a red scheduled job
with nobody watching is the exact failure mode PITFALLS #8 warns about, and the
~4-weekly cadence is a standing operational item for after v4.0, not a Phase 3
deliverable.

One input, `tag`, required, defaulting to the currently pinned
`FIREFOX_153_1_0esr_RELEASE` so a dispatch with no thought still exercises the
replay against a known-good tag.

One job on `ubuntu-latest`: check out the repo, free disk space before cloning
(the shallow Gecko clone is roughly 6.7 GB of pack plus working tree against a
standard runner's headroom — remove the preinstalled toolchain caches the
runner image ships if the checkout fails on space), then run
`bash scripts/rebase-upstream.sh --tag "${{ inputs.tag }}"`. The job fails if
that script fails; add no `continue-on-error` and no `|| true`.

Do **not** install Nix and do **not** attempt a Gecko build in CI: the Nix
Gecko toolchain closure does not fit a standard runner alongside a 5.6 GB Gecko
working tree. State that limitation in a comment at the top of the workflow,
and state that the `toolchain-baseline.txt` diff PITFALLS #2 requires is
therefore an operator step run locally after a successful CI replay. An honest
stated limitation is the deliverable; a silently omitted step is not.

**Do not dispatch the workflow from this plan.** `workflow_dispatch` only
registers a workflow that is present on the repo's **default branch**, and
`origin/master` is currently 101 commits behind with zero registered workflows
(`gh api repos/Deocracy/Sourcerer/actions/workflows --jq .total_count` returns
0). A dispatch from here would fail with "could not find any workflows named
…", and the only route to a green dispatch is a `git push` — which at this wave
would also publish plan `03-02`'s concurrent commits to a public repo. The real
dispatch therefore lives in plan `03-06`, after every plan has committed, where
the push is an explicit, consequence-stated step.

Verify here at file-shape level only: the YAML parses, the trigger and absent
keys check out, and `gh workflow view rebase-upstream.yml` is expected to report
the workflow as not yet registered — record that expected state so `03-06` knows
