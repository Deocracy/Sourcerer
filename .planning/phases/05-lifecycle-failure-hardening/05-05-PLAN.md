<recorded_decisions>
- **Gate shape (D-127):** a `--gate` flag on this phase's own script, not a new
  sibling driver. The established rule in this repo is one verification script
  per phase, extended never siblinged; a separate gate script would be a fourth
  driver to keep in sync with three others.
- **The known-open exclusion:** the Phase 3 endpoint-allowlist check is red today
  under broken-windows ledger entry 5, which CONTEXT.md explicitly places outside
  this phase's scope — it needs a product and privacy decision about three hosts a
  working shell newly reaches, not a code change. The gate therefore runs the
  Phase 3 script in full, and reports that one check as a **named known-open
  exclusion carrying its ledger id and reason**, distinct in the output from both
  a pass and a failure. Any other red check fails the gate outright. The exclusion
  is keyed on the ledger entry: if entry 5 is later fixed or waived, the exclusion
  stops applying and the check must be green.
- **Human item (D-126):** one full working day, recorded by the developer. Not a
  multi-day soak, which would gate the milestone on calendar time, and not an
  automated soak, which is repeatable but exercises nothing that "daily-drivable"
  actually means.
</recorded_decisions>

Add a `--gate` flag to `scripts/verify-phase-05.sh`'s existing argument loop,
alongside `--quick` and `--only`. Reject any combination of `--gate` with the
other two with a named error rather than silently preferring one.

In gate mode the script first runs its own full check set exactly as it does
today, then invokes `scripts/verify-phase-04.sh` and `scripts/verify-phase-03.sh`
as external scripts under the same process-group discipline every other external
invocation in the file already uses, capturing each script's output and exit
status.

Build one aggregate summary with three sections, one per phase script, then a
single verdict line. A phase script exiting zero is a pass. A phase script exiting
non-zero is a failure **unless** every failing check inside it appears in the
known-open exclusion list; in that case it is reported as passing-with-exclusions,
and each excluded check is printed on its own line naming the check label, the
broken-windows ledger entry id that justifies it, and a one-line reason. Seed the
exclusion list with exactly one entry: the Phase 3 endpoint-allowlist check under
ledger entry 5. Any failing check that is not on that list fails the gate.

Guard the exclusion against outliving its justification: before applying it, read
the ledger and confirm the referenced entry is still open. If the entry has been
fixed or waived, the exclusion no longer applies and the check must be green — say
so in the output and fail.

Print the current commit identifier once at the top of the gate output, so the
"all green at the same commit" claim is evidenced by the artifact rather than
asserted by a person.

Extract the failing-check labels from each script's output by matching the summary
lines those scripts already print, rather than by rerunning individual checks.

Record the total gate runtime and write it into `05-VALIDATION.md`'s estimated
runtime field, replacing the placeholder, and set that document's compliance and
wave-zero flags to reflect the finished state.
