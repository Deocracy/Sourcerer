<assumption_delta_decision>
**Signal:** the assumption-delta detector fired `pluralization` on the term
`second`, from success criterion 2 — "Launching Sourcerer while it is already
running focuses the existing window and spawns no second backend."

**Noun now primary:** none. There is no new general identity here.

**Decision: `no-change`.** The word "second" appears in this phase exclusively as
the thing the phase exists to *prevent*. Nothing in scope introduces a second
instance of anything: D-121 makes the supervisor's start idempotent, D-123 states
plainly that a second shell window is never opened, and CONTEXT.md's deferred list
puts "a second shell window sharing one backend" firmly post-4.0. The identity
model stays exactly what Phase 4 established — one browser session, one pinned
port, one token, one backend — and this phase's work makes that singularity
enforced rather than incidental. Generalising to an N-instance identity here would
invent multi-window semantics ahead of the chrome-owned tab model, which is the
precise thing D-123 declines to do.

The single-instance invariant is encoded as a runnable assertion rather than a
comment: the `side05-no-second-backend` check in this plan fails the moment a
second backend appears, so a future phase that reintroduces multiplicity goes red
immediately and has to make the choice deliberately.
</assumption_delta_decision>

<objective>
Make a second launch of Sourcerer focus the window that is already open, and make
a second backend impossible to spawn even if something else ever opens a shell
window.

Purpose: SIDE-05 is the last of the four requirements, and the failure it prevents
is the worst one in daily use — two backends fighting over the same config
directory while the developer stares at a blank second window.

Output: a command-line handler registered ahead of the stock one, an idempotent
supervisor entry point, and an automated check that runs on a real display because
the platform's remoting is compiled out of the headless path.
</objective>

<recorded_decisions>
Discretionary choices locked (CONTEXT.md "Claude's Discretion"):

- **Registration mechanism (the item CONTEXT.md handed to research):** a static
  XPCOM manifest entry, not runtime registration. The category is enumerated in
  ascending string order of the entry name, which is exactly why every stock
  handler carries a sort-order prefix; `a-sourcerer` sorts ahead of the stock
  browser handler and far ahead of the default handler that actually opens the
  window. Registration needs no new patch: the shell directory is already a
  first-class member of the browser build's directory list, so the manifest
  declaration and the manifest file both live inside the project's own tree.
- **Where the handler class lives:** exported from `SourcererAPI.sys.mjs` itself,
  not a new sibling module. The handler needs the interface-constant and
  query-interface helpers that the boundary guard forbids everywhere under the
  shell directory except that one file. A sibling module would be a real
  internals touch outside the boundary — the exact hole SHELL-02 exists to close.
- **Handler behaviour (D-121/D-123/D-124):** look up the existing shell window by
  the window type the document already declares. If none is found, do nothing at
  all — this is the first launch and preventing the default would leave the user
  with no window. If one is found, focus it and set the prevent-default flag, and
  ignore every command-line argument. Never open a window.
- **Build tier:** this is the one **tier 3** change in the phase. A manifest entry
  feeds a generated component table that is compiled and linked into the platform
  library, so a full build is required — not the fast preprocessing tier.
  CONTEXT.md's expectation that nothing here needs tier 3 was scoped to build
  configuration changes; this is a different trigger. The build is incremental,
  so expect minutes rather than the cold-clone figure recorded in the build docs.
- **Verification display:** every check in this plan launches without the headless
  flag, on a real or virtual display. Headless mode disables the client half of
  the remoting protocol outright, so a headless single-instance check would start
  two independent instances and prove nothing at all.
</recorded_decisions>

Add two checks to `scripts/verify-phase-05.sh`, both outside the quick set and
both launched through the non-headless helper.

`side05-second-launch-focuses` creates one profile directory and uses it for
**both** launches — the platform keys remoting on the profile path, so two
different profiles would never remote into each other and the check would prove
nothing. It launches the shell, waits for the backend-ready sentinel, then runs
the same binary a second time against the same profile with no arguments and
waits for that second process to exit. It asserts three things: the second
process exited rather than running on as an independent instance; the first
process is still running; and no second window was opened, which is observable as
the absence of a second shell-ready sentinel in the first process's log and the
absence of any window-opening error.

`side05-no-second-backend` runs in the same launched session and is the invariant
assertion: across both launches exactly one backend-ready sentinel was emitted,
the announced backend pid is unchanged, and a process count for the backend entry
file returns one. Pair it with its positive control in the same check: launch a
third instance against a **different** profile directory, assert that one *does*
start its own window and its own backend, then stop it — this is what proves the
guard is scoped to the profile and has not simply disabled second launches
globally.

Both checks must assert the first launch actually reached readiness before
drawing any conclusion, so neither can pass vacuously against a launch that never
started. Tear down every process and every profile directory through the script's
existing tracked-resource and process-group cleanup path.
