<objective>
Ship `@sourcerer/tab-uris`: the `factoryId → URI` registry that gives every
shell tab an address, and the `view:` / `settings:` open handler that turns a
typed address back into the right tab in the right panel.

Purpose: URI-01 and URI-03 are the phase's real engineering. Everything they
need already exists in the widget manager, the opener service and the view
contributions — this is composition plus one small registry, not a new
subsystem. The registry is also the single interface the post-4.0 browser
bridge consumes, which makes its public shape the most consequential thing
this phase produces.

Output: `view:` and `settings:` round-trip for every shipped widget that owns
a shell tab.

    interface — treat its exported shape as an API, because the post-4.0 browser
    bridge consumes it.

    hard-coding twenty imports: inject the contribution provider for command
    contributions, filter to instances of `AbstractViewContribution`, and index
    them by `effectiveWidgetId`. `bindViewContribution` binds every view
    contribution as a command contribution, so this reaches all of them, and it
    picks up plugin-contributed and future views for free. Resolve the provider
    lazily on first use, never during container-module load: the provider caches
    its array on first call and drops its container reference, so an early call
    would freeze an incomplete set.

    first initializes, and report every table entry with no matching
    contribution, by name, at error level. That cross-check is what converts a

    nothing at exactly the moment a human types it — into a startup complaint.

      contribution, and call its `openView` with the open/reveal/activate
      vocabulary the opener options carry. Do not invent another vocabulary and
      do not write any dedup: the widget manager already keys on the factory id
      plus options, already guards the concurrent-open race with its pending
      promise map, and already restores. For a path beginning with the plugin
      view container prefix and no matching contribution, resolve through the
      widget manager using the derived identifier — the identifier's own id

      locally rather than reaching for the plugin registry's protected helpers.

## Deviation recorded

`02-CONTEXT.md` D-50 describes the `view:` table as "a static map plus a plugin
registry lookup". This plan ships the static table as a **coverage contract**
that is cross-checked at startup, while resolution itself discovers view
contributions at runtime from the container. Reason: the static-map-as-lookup
form's known failure mode is a mis-transcribed string producing a URI that
silently no-ops, which `02-RESEARCH.md` names as this phase's most likely
mistake; runtime discovery removes that class of bug entirely while the retained
static table preserves D-50's drift protection and its documentation value. If a
reviewer prefers the literal static-map lookup, it is a drop-in replacement for
one method.
